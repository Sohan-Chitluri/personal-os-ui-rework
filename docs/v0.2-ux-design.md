# Personal OS v0.2 — UX & Interface Design Analysis

Status: PROPOSAL — awaiting approval. No implementation has begun.
Author: Morales (design pass)
Scope: UX architecture only. Infrastructure is frozen unless a UX requirement forces a change.

---

## 0. A blocking correctness finding (read first)

Priority 2 says: *"Sending a message should ALWAYS append the raw message to the Daily
Stream, timestamp it, preserve it forever, THEN invoke the processor. Never process before
capture."*

The current TUI **violates this today.** In `app.py::on_entry_captured` (line 577) the flow is:

```
add_user_message(text)         # shown in chat
result = await process_entry(text, source)   # processed
```

There is **no `vault.append_journal_entry()` call.** The raw message is processed but never
persisted to the Daily Stream. Only the CLI (`pos note`) and the voice skill capture-first.
So the TUI — the primary interface — is the one path that loses raw captures.

This is not a redesign question; it is a data-integrity bug against the v0.2 mandate. It must
be fixed regardless of which UI concept we pick. I call it out here so it is not buried inside
a UI rewrite.

**Capture contract (applies to every input path — text, voice, CLI):**

```
1. append_journal_entry(raw_text, timestamp, source)   # durable, atomic, git-committed
2. return capture receipt to UI (entry id / path / timestamp)
3. THEN enqueue processing (async, non-blocking)
4. processing failure NEVER loses the raw capture
```

Capture and processing become two decoupled stages. Capture is synchronous and guaranteed;
processing is best-effort and retryable. This is the single most important architectural
change in v0.2.

## 1. UX analysis — what's wrong with the prototype

The current TUI proved the architecture (chat + 6 stacked sidebar panels, F1–F6). Treating it
as a prototype, its friction points against the "capture is effortless" goal:

1. **Capture and navigation share one surface.** The chat input is always-on and 8 rows tall,
   but capture (the #1 job) has no dedicated, instant, mode. You must be focused in the right
   widget. There's no global "capture from anywhere" key.

2. **No voice capture in the TUI at all.** `Ctrl+V` posts an `EntryCaptured` message path that
   isn't wired to the voice skill. Voice — Priority 1 — is CLI-only right now.

3. **Selecting a project emits chat noise.** `on_project_selected` does
   `_add_system_message("📁 Selected project: X")`. The spec explicitly forbids this. Selection
   should change the *workspace*, not talk to you.

4. **The sidebar is a panel switcher, not a navigator.** F1–F6 swap which single panel is
   visible in the 25% column. There's no persistent "where am I" tree, no Today / Journal /
   Knowledge / Reviews / Favorites. The center pane is locked to chat forever.

5. **The center pane can only be chat.** The spec wants the center to render Markdown,
   dashboards, Tasks.md, Timeline.md, a Weekly Review, etc. depending on context. Today it is
   hardcoded to `ChatHistory`.

6. **No developer/trace mode.** Processing is a black box; when extraction misroutes (the
   alias-map class of bug), there's no visible trace.

7. **"Coming soon" stubs everywhere.** ~10 handlers just post a system message. They set the
   expectation that the sidebar is interactive when it mostly isn't.

The through-line: the prototype is **chat-first**. The spec wants **capture-first, workspace-
navigable**, with conversation as *one* possible center-pane view — not the whole app.

## 2. Design principles derived from the brief

- **Capture is a mode, not a widget.** One key, from anywhere, always available.
- **Raw first, always.** Persist before you process. The stream is the source of truth.
- **Navigation is modal + keyboard-first** (Yazi/lazygit muscle memory), not mouse tabs.
- **The center pane is a router.** Its content is a function of the selected sidebar node.
- **Selection is silent.** Changing workspace never emits chat.
- **Conversation is a view, not the app.** It lives in the center pane like any other view.
- **Developer detail is opt-in** and hidden by default.

## 3. Three interface concepts

### Concept A — "Yazi-style Miller navigator"

Three vertical columns, like Yazi's file manager.

```
┌───────────┬────────────────────┬─────────────────────────┐
│ SECTIONS  │  LIST (context)    │  PREVIEW / CENTER        │
│           │                    │                          │
│ > Today   │  Maestro       ●   │  # Maestro               │
│   Projects│  Drone         ●   │  Phase: scheduler        │
│   Tasks   │  BlindGuard    ○   │  Health: green           │
│   Journal │  VLSI          ●   │  Open tasks: 4           │
│   Knowledge│ FPGA          ○   │  ...rendered README...   │
│   Reviews │                    │                          │
│   Favorites                    │                          │
│   Settings│                    │                          │
└───────────┴────────────────────┴─────────────────────────┘
 [Space] capture   [/] search   [Tab] focus   [d] dev   [q] quit
```

- Column 1: the workspace sections (the spec's sidebar list).
- Column 2: contents of the selected section (projects, task list, journal dates…).
- Column 3: preview/render of the highlighted item (Markdown, dashboard).
- `h/j/k/l` or arrows move; `l`/Enter descends, `h` ascends — exactly Yazi.
- Capture is an overlay (Space) that floats over all three columns and returns you exactly
  where you were.
- Conversation is the center-pane view when you're on "Today" or a project's chat.

Strengths: instantly familiar to Yazi users; preview-as-you-move makes retrieval fast; capture
never disturbs layout. Weaknesses: three columns is tight in an 80-col terminal; conversation
(a tall scrolling view) fits awkwardly in a narrow 3rd column.

### Concept B — "lazygit-style two-pane workspace" (RECOMMENDED)

A persistent left sidebar (navigator tree) + a large center pane that *routes* to different
views. Capture and dev are overlays. This is lazygit's model: a narrow panel column on the
left, a big context pane on the right, everything keyboard-driven, number keys jump panels.

```
┌──────────────┬──────────────────────────────────────────────┐
│ NAVIGATOR    │  CENTER PANE (routed view)                    │
│              │                                               │
│ ▸ Today      │  ┌─ Conversation ─────────────────────────┐  │
│ ▾ Projects   │  │ 09:14  you                              │  │
│    Maestro ● │  │   fixed streaming retry in providers    │  │
│    Drone   ● │  │ 09:14  os                               │  │
│    VLSI    ○ │  │   ✅ Progress → Maestro (+1)            │  │
│   Tasks      │  │                                          │  │
│   Journal    │  └──────────────────────────────────────────┘ │
│   Knowledge  │                                               │
│   Reviews    │  (or: rendered Tasks.md / Timeline / Review / │
│   Favorites  │       dashboard, depending on selection)      │
│   Settings   │                                               │
├──────────────┴──────────────────────────────────────────────┤
│ Today: 7 captures · 4 tasks · Maestro ●    [Space]capture … │
└──────────────────────────────────────────────────────────────┘
```

- Left navigator is always visible (toggle with `Ctrl+B`); a Tree with sections + expandable
  children. `j/k` move, Enter/`l` selects, silently swapping the center view.
- Center pane is a **ViewRouter**: one of `ConversationView`, `MarkdownView`,
  `DashboardView`, `TaskListView`, `ReviewView`. Selecting a nav node sets the view.
- **Capture overlay** (Space): minimal modal, text or voice, closes back to prior view.
- **Developer panel** (`d`): a bottom drawer or right split showing the processing trace for
  the last capture — extraction steps, routing, timings. Hidden by default.
- Status bar shows today's capture count + contextual keys.

Strengths: matches the spec almost line-for-line (persistent sidebar navigator, context-driven
center pane, overlays for capture/dev); conversation gets a full-width pane; degrades
gracefully at 80 cols (sidebar can collapse). Weaknesses: less "novel" than A; the ViewRouter
is the main new abstraction to build well.

### Concept C — "btop-style dashboard-first"

Landing view is a live dashboard (today's captures, task burndown, project health tiles,
recent activity), à la btop. Navigation drills from tiles into detail. Capture is a persistent
bottom bar.

```
┌─ TODAY ────────────┬─ PROJECTS ─────────┬─ TASKS ──────────┐
│ 7 captures         │ Maestro    ● 4     │ ☐ wire voice UX  │
│ last 09:14         │ Drone      ● 2     │ ☐ fix capture bug│
│ ▁▂▅▇▅▂ activity    │ VLSI       ○ 0     │ ☑ tag v0.1.0     │
├────────────────────┴────────────────────┴──────────────────┤
│ RECENT STREAM                                               │
│ 09:14 fixed streaming retry…                               │
│ 08:50 idea: compress context via…                          │
├────────────────────────────────────────────────────────────┤
│ ▸ capture ▁ (Space voice / type here)                      │
└────────────────────────────────────────────────────────────┘
```

Strengths: beautiful "at a glance" overview; great for the morning "what's up" moment.
Weaknesses: dashboards are a *retrieval/overview* tool, not a *capture* tool; capture-first is
the stated #1 goal and a dashboard buries it. Also the most work to build and the least
keyboard-navigable for deep editing. Better as a *view within* B (the "Today" dashboard) than
as the whole app.

## 4. Critique matrix

| Criterion (weight)              | A: Yazi 3-col | B: lazygit 2-pane | C: btop dash |
|---------------------------------|:-------------:|:-----------------:|:------------:|
| Capture friction → near zero (×3)|   good        |   **best**        |   fair       |
| Matches spec's sidebar+center (×3)| partial      |   **exact**       |   partial    |
| Conversation as a view (×2)     |   awkward     |   **best**        |   fair       |
| Keyboard-first navigation (×2)  |   **best**    |   best            |   fair       |
| 80-col terminal resilience (×1) |   poor        |   **good**        |   fair       |
| Dev/trace mode fit (×1)         |   fair        |   **best**        |   fair       |
| Retrieval / overview (×1)       |   good        |   good            |   **best**   |
| Build cost / risk (×1, lower=better)| medium    |   medium          |   high       |

**Weighted winner: Concept B.** It matches the written spec most literally (persistent
navigator sidebar, context-routed center pane, capture + dev as overlays), gives conversation
a proper home, and survives narrow terminals. Concept C's dashboard is too good to discard —
so fold it in as the **"Today" view inside B**. Concept A's move-to-preview is worth stealing
as an *optional* behavior when the navigator is focused (preview the highlighted node).

## 5. Recommended architecture (Concept B + Today dashboard from C + preview from A)

### 5.1 Layout
- `NavigatorSidebar` (left, persistent, Tree): Today · Projects · Tasks · Journal · Knowledge ·
  Reviews · Favorites · Settings. Collapsible (`Ctrl+B`).
- `CenterPane` = **ViewRouter** hosting exactly one view at a time:
  - `TodayView` (dashboard: capture count, activity, task summary, project health) ← from C
  - `ConversationView` (the chat stream for Today or a project)
  - `MarkdownView` (renders README/Tasks/Timeline/any .md)
  - `ReviewView` (weekly/daily review render)
  - `SettingsView`
- `StatusBar` (bottom): today's capture count + contextual keybinds.

### 5.2 Modes
- **Explore mode** (default): navigate sidebar, read center pane. Selection is silent.
- **Capture mode** (`Space` from anywhere): minimal overlay modal.
  - Voice sub-flow (Priority 1): `Space` start rec → indicator → `Space` stop → transcribe →
    transcript preview → `Enter` accept / `E` edit / `R` re-record / `Esc` cancel.
  - Text sub-flow: type → `Enter` accept.
  - On accept: **append_journal_entry FIRST** (capture contract §0), close overlay, return to
    prior view, then process async. A toast/status shows the processing result.
- **Developer mode** (`d`, toggle): bottom drawer showing last-capture trace (raw text →
  extractions → routing → files touched → timings). Hidden by default.

### 5.3 The capture contract (shared by voice + text + CLI)
Introduce a single `capture(raw, source) -> CaptureReceipt` in core that:
1. `vault.append_journal_entry(raw, ts, source)` (atomic, committed) — **always first**
2. returns receipt (path, timestamp)
3. enqueues `process_entry` on the existing `BackgroundProcessor`
4. surfaces the processing summary via a message/toast when done
Both the TUI overlay and `pos note`/`pos voice` call this one function. Fixes the §0 bug and
guarantees capture-before-process everywhere by construction.

### 5.4 Keymap (Yazi/lazygit-flavored)
```
Space   capture overlay (global)
/       search (global)
j/k ↑↓  move in navigator / scroll view
l Enter select / descend (silent workspace change)
h       ascend / collapse
Tab     toggle focus navigator ⇄ center
1..8    jump to nav section (Today..Settings)
d       toggle developer trace
Ctrl+B  toggle sidebar
g/G     top / bottom
q       quit  (Ctrl+Q hard quit)
```

### 5.5 What we reuse (infra frozen)
- `VaultManager`, `BackgroundProcessor`, `process_entry`, `SearchEngine`, config — unchanged.
- Voice skill's `record_audio`/`transcribe` reused; only a TUI-driven start/stop wrapper is
  new (current skill is fixed-duration; overlay needs press-to-start/press-to-stop — a small
  additive wrapper, no change to existing functions).
- Existing panels become *views* or feed the navigator; their data methods are kept.

### 5.6 Rough build order (for later, after approval)
1. `capture()` core contract + fix TUI capture-before-process (the §0 bug). [correctness]
2. `NavigatorSidebar` + `ViewRouter` skeleton; silent selection. [shell]
3. `TodayView` + `ConversationView` + `MarkdownView`. [core views]
4. Capture overlay (text path). [capture mode]
5. Voice press-to-start/stop wrapper + voice sub-flow in overlay. [Priority 1]
6. Developer trace drawer. [dev mode]
7. Reviews/Knowledge/Favorites views. [breadth]

Each step is independently verifiable and maps to a concurrent workstream if we parallelize.
